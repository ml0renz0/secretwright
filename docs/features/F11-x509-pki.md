# F11 — Certificados X.509 y PKI

## Alcance

Inspección y validación local de certificados, claves privadas y solicitudes CSR con las bibliotecas criptográficas de Go. Generación de una clave y CSR locales. Lectura, emisión, firma y revocación mediante un montaje PKI y un rol existentes en Vault.

No se necesitan OpenSSL ni un daemon. La administración de CAs, montajes y roles queda fuera de estos comandos. Los ejemplos de pruebas preparan su propia CA efímera; no modifican instalaciones existentes.

## Peticiones YAML y JSON

```yaml
api_version: secretwright/pki/v1
name: web
common_name: web.example.test
dns_names: [web.example.test]
ip_addresses: [127.0.0.1]
ttl: 1h
usage: server-auth
key:
  type: ecdsa
  bits: 256
```

El manifiesto es estricto y versionado. Rechaza campos desconocidos, duplicados, aliases, varios documentos y tipos ambiguos; no ejecuta funciones ni interpolaciones. La entrada tiene límites de 1 MiB, 64 niveles y 10 000 nodos. `schemas/pki-v1.schema.json` publica el mismo JSON Schema Draft 2020-12 embebido, con ID `urn:secretwright:pki:v1`, sin referencias externas.

Se exige al menos un SAN DNS o IP y se permiten hasta 64 en total. Los nombres DNS son exactos, sin comodines ni URLs; las IP se normalizan. El CN es opcional y debe estar también entre los SAN. Los tiempos son segundos enteros positivos, hasta 24 horas. El uso es `server-auth` o `client-auth`.

La clave predeterminada es ECDSA P-256; también se admiten P-384, RSA 2048/3072/4096 y Ed25519. El rol Vault debe permitir las identidades y el TTL solicitados y emitir el tipo de clave seleccionado. Una respuesta que no cumpla la petición se rechaza después de la emisión, sin presentarla como válida.

```bash
secretwright pki schema
secretwright pki example > request.yaml
secretwright pki example --format json > request.json
secretwright pki validate --file request.yaml
```

YAML es el formato predeterminado de las peticiones generadas; JSON se selecciona explícitamente. Certificados, claves y CSR conservan PEM estándar. Los informes y los JSON Schema son JSON.

## Inspección y verificación local

```bash
secretwright pki cert inspect --file server.pem
secretwright pki key inspect --file server.key
secretwright pki csr inspect --file server.csr
secretwright pki cert match --file server.pem --key server.key

secretwright pki cert verify --file server.pem --ca-file roots.pem \
  --chain intermediates.pem --hostname web.example.test --usage server-auth
```

Inspect devuelve metadatos públicos: sujeto, emisor, serial, SAN, fechas, estado temporal, algoritmo y huellas SHA-256. No imprime PEM ni componentes privados. La inspección de un certificado caducado permite ver sus metadatos; verificarlo comunica un resultado negativo.

Verify comprueba firma, cadena, restricciones de CA, tiempo, uso y hostname o IP cuando se especifica. Solo confía en las raíces proporcionadas con `--ca-file`: una raíz añadida a la cadena no adquiere confianza por estar allí. No utiliza el almacén del sistema ni descarga AIA, CRL u OCSP. El informe declara `revocation_checked: false`: `crypto/x509.Verify` no comprueba revocación automáticamente.

Match compara las claves públicas del certificado y la clave privada. La firma de una CSR se verifica incluso al inspeccionarla. Los errores tienen motivos aprobados, sin textos arbitrarios del parser o del servidor.

Los archivos PEM deben estar completos, sin basura ni cabeceras inesperadas. Se aceptan hasta 32 certificados y 1 MiB por documento. Una clave individual está limitada a 64 KiB. Se admiten PKCS#1 RSA, SEC1 EC y PKCS#8 RSA/EC/Ed25519 sin cifrado; no se admiten PKCS#12 ni claves cifradas.

Un archivo de identidad puede contener una clave privada y la cadena que le corresponde. Se comprueba que coincida con el primer certificado y se exige `0600` al leerlo. Una CSR contiene únicamente su bloque de petición, sin una clave privada añadida. Las raíces e intermedias contienen solo certificados.

## Crear y firmar una CSR

```bash
secretwright pki csr create --file request.yaml \
  --out server.csr --key-out server.key

secretwright pki sign --mount pki --role web --file request.yaml \
  --csr server.csr --ca-file roots.pem --out server.pem --token-file operator-token
```

Create reserva ambas salidas antes de generar material criptográfico; no sobrescribe archivos existentes. Publica primero la clave privada `0600` y después la CSR, también privada. La pareja no es una transacción atómica: si la clave ya se guardó y falla la CSR, se conserva la clave y se devuelve resultado parcial.

Sign valida localmente la CSR contra el manifiesto antes de contactar con Vault. Solo envía la CSR; la clave permanece local. La respuesta debe conservar su clave pública, CN y SAN, tener el uso solicitado y encadenar con las raíces elegidas.

## Leer, emitir y revocar

```bash
secretwright pki ca --mount pki --out ca.pem --token-file operator-token
secretwright pki read --mount pki --serial 01:ab:cd \
  --out existing.pem --token-file operator-token

secretwright pki issue --mount pki --role web --file request.yaml \
  --ca-file roots.pem --out identity.pem --token-file operator-token

secretwright pki revoke --mount pki --file server.pem --force --token-file operator-token
```

La raíz de confianza se selecciona explícitamente; obtener un certificado CA del servidor es una lectura, no una decisión automática de confiar en él. Issue guarda un único PEM privado con clave, certificado y cadena, utilizable como identidad TLS. Sign guarda certificado y cadena, sin clave.

El TTL real se calcula a partir de `NotAfter`, contrastado con `expiration` de Vault. No se toma de `lease_duration`, que puede ser cero en PKI. La respuesta debe contener un certificado leaf, una cadena válida, identidades exactas y una clave correspondiente.

Revoke exige `--force` antes de cargar credenciales. Deriva el serial del certificado local, lee el certificado de ese montaje y compara la huella antes de revocar, para evitar actuar sobre otro certificado con el mismo serial. No revoca CAs ni acepta prefijos. Su informe acredita el resultado de Vault; los consumidores deben aplicar sus propias comprobaciones de revocación.

## Archivos, fallos y shell

Todos los archivos son rutas reales; no se acepta `-` ni stdin. Las claves y los archivos de identidad requieren `0600`, sin symlinks finales. Las salidas son nuevas, exclusivas y privadas; los inputs locales y la reserva de las salidas se validan antes de seleccionar el token o iniciar HTTP.

Una emisión o firma cambia Vault aunque falle después el guardado local. Un resultado incierto, una respuesta de emisión inválida o un fallo de publicación tras emitir devuelve `5`. No se repite la petición ni se revoca automáticamente: puede existir un certificado válido hasta su TTL finito y el operador debe inspeccionarlo o retirarlo explícitamente. Nunca se imprime la clave para intentar recuperarla.

Los comandos online utilizan dirección, namespace, timeout y token-file existentes; el timeout cubre la operación completa. Los comandos offline no seleccionan credenciales ni interpretan la configuración de Vault. La shell mantiene su conexión fija y no añade ningún comando PKI al historial; el autocompletado solo ofrece el nombre del grupo.

Códigos: `0` éxito; `1` entrada/configuración/archivo; `2` autenticación o permisos; `3` ausente; `4` verificación negativa, clave distinta o conflicto; `5` resultado parcial o incierto; `130` cancelación previa a efectos. Se detectan errores y escrituras cortas de stdout.

## Aceptación

Contrato y pruebas se publican antes de implementar. Se exige:

- Fixtures criptográficas nativas: raíz, intermedia, leaf, CSR y claves, sin OpenSSL.
- Cadena, SAN DNS/IP, tiempo, EKU y claves correctos; rechazo de raíz ajena, cadena incompleta, nombres incorrectos, caducidad, firmas alteradas y claves distintas.
- PEM estricto, límites, claves cifradas y archivos públicos o enlaces rechazados; informes sin claves ni PEM.
- Vault real con rol y token acotados: emisión y handshake TLS, firma con clave local y permisos efectivos.
- Revocación comprobada mediante registro y CRL firmada que contiene el serial; sin afirmar que Verify o TLS comprueban CRL automáticamente.
- Respuestas perdidas sin reintentos, resultados parciales, salidas privadas y validación local antes de HTTP.
- YAML por defecto/JSON explícito, smoke del ejecutable y shell, fuzzing y regresión completa F00–F10, incluido PostgreSQL efímero obligatorio.
